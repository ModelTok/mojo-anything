# Decisions

Choices made so far, with reasons. Each one can be revisited.

mojo-anything is a fork of rust-anything. Entries from rust-anything that no longer describe the
tool are kept and marked **Superseded**, with what replaced them; "Rust era" in an entry means
rust-anything before the fork. The design is
[`docs/superpowers/specs/2026-11-21-mojo-anything-design.md`](docs/superpowers/specs/2026-11-21-mojo-anything-design.md),
and the plans that carried it out are under `docs/superpowers/plans/`.

## mojo-anything (the design and Milestones 1-7)

| # | Decision | Reason |
| --- | --- | --- |
| F1 | mojo-anything ports code into Mojo, and is itself to be written in Mojo. Phase 1 retargets the Rust tool so that everything it generates, builds and gates is Mojo; Phase 2 ports the retargeted tool to Mojo command by command, proven against recordings of the Phase 1 binary. Of the approaches weighed, the whole tool is ported with its own method (B), not a fresh Mojo core for Python alone (A) or a Mojo CLI over the Rust engine (C). | The user chose the order. Retargeting first means the Rust-only generators (napi, PyO3, magnus, cargo builds, the clippy gate) are replaced once in Rust and never ported, and the Phase 1 binary's recordings become Phase 2's specification. B keeps every feature Mojo can support; C would leave most of the tool in Rust, against "written in Mojo". |
| F2 | Only Rust is ruled out. CPython reached through Mojo's Python interop and generated C shims (the Node-API shim, `wasm_runtime.c`) are allowed in what mojo-anything generates and in the finished tool. Nothing mojo-anything generates is Rust. | Decided by the user (2026-11-21). Node-API, Fiddle, cgo and FFM are each language's own C route, and Phase 2 needs tree-sitter and regular expressions through Python; ruling those out would leave no route for several languages. |
| F3 | Mojo is pinned to 1.2.0 through pixi: in the repository's `pixi.toml` and `pixi.lock`, in `crate::mojo::MOJO_VERSION`, and in every generated unit's `pixi.toml` (channels `https://conda.modular.com/max`, then `conda-forge`). Every API the generated code uses is checked against the 1.2.0 compiler and listed in `docs/mojo-notes.md`. | Mojo changes between releases (`mojo package` became `precompile`, `UnsafePointer` is deprecated, there is no `mojo test` in 1.2), so pretrained knowledge and the nightly stdlib source are not enough; a `.mojoc` is tied to the compiler that wrote it, and EmberJson's release pins the same Mojo. |
| F4 | Structured values cross as JSON through one Mojo dispatcher (`mojo_anything_call`, `mojo_anything_free`) on EmberJson 0.5.0 behind `json.mojo`, emitted only into units that need it. What EmberJson cannot carry faithfully is refused with a named error, never guessed: lone surrogates, integers beyond 64 bits for Ruby, and in Go invalid UTF-8; NaN, the infinities and -0 cross as `$num` markers. EmberJson comes from its git tag through pixi-build. | The design's rules for the JSON (exact float round trip, key order, no depth limit) hold on EmberJson, checked by `tests/mojo_json.rs`; a silent substitute (a bignum read as a float, U+FFFD for a bad byte) would pass as a wrong answer. The conda package (0.4.0) was built for Mojo 1.1 and does not load under 1.2.0. |
| F5 | Java and Kotlin call the port through the Foreign Function & Memory API, so Java and Kotlin units need Java 22 or newer (M14). | Decided by the user (2026-11-21); FFM needs no native code on the Java side, where JNI needed Rust. |
| F6 | Linux now, macOS later: Phase 1 closes on Linux. The code is written for macOS too (the front doors' Darwin texts type-check on Linux), but nothing is built, linked or run on a Mac, the macOS CI job runs for the first time after publication, and the docs list macOS as not run. | Decided by the user (2026-11-22: "Linux now, macOS later"). No macOS machine is available, and CI needs the GitHub repository. |
| F7 | No native Windows and no Android. On Windows the tool runs in WSL; `doctor` on Windows fails its `pixi` and `mojo` rows and points at the WSL clone; the npm launcher stops on Windows naming WSL. Android (`--profile android`, on-device recording) is removed. | Mojo builds only on Linux and macOS, and does not target Android, so a port could not run there. |
| F8 | Release platforms are linux-x64, linux-arm64 and darwin-arm64 (darwin-x64 only if the pinned Mojo ships for it). `package` writes files and workflows only: it never builds for another platform and never publishes. | A package can only carry a library Mojo can build, and publishing is outward-facing: each publish, push and registry entry is asked for in chat. |
| F9 | The repository is `ModelTok/mojo-anything` (MCP server `io.github.ModelTok/mojo-anything`), not the design's `Tokarzewski/mojo-anything`. `upstream` stays rust-anything for merging fixes during Phase 1; no pull requests go upstream. | Decided by the user (2026-11-22: "publisj mojo-anything on modeltok org"). mojo-anything is a separate product, not a contribution to rust-anything. |
| F10 | Phase 1 ends with the annotated tag `v0.1.0`; Phase 2 records that tagged binary, so its specification does not move. | Calls made after the builder check: a moving Phase 1 would change the recordings Phase 2 is proven against. |
| F11 | Every number in the docs is measured on Mojo and names its log under `docs/measurements/` (`scripts/check-doc-numbers.py`, run by `cargo test`); rust-anything's results stay only as labelled history; no Mojo timing is published until `bench` has run twice on a quiet machine. | Anti-goal of the design: a claim not measured on Mojo. The measurement runs of 2026-11-22 were on a busy machine, so they checked correctness and sizes only. |
| F12 | The binary wires and the native batch classes are dropped from Phase 1; `--batch` is retargeted (TS/JS through the dispatcher, S17; Go, Ruby, Java and Kotlin answer "not yet"), and `--kind wasm` came after the Node-API route worked (M13). | Correctness first: the wires and native batches were speed features written in Rust, and come back only where `bench` shows a crossing worth speeding up on Mojo. |
| F13 | `gate` on a Mojo port checks `mojo format` (no check mode in 1.2, so a formatted copy is compared), a `--Werror` build, the unit's `test_*.mojo` (run with `mojo run`, there being no `mojo test`), no stub left, every `abort`, pointer and `external_call` explained by a `# SAFETY:` comment, the size, the built module's API and the replay against the built module. | The design's definition of done, adapted from rust-anything's fmt, clippy, cargo test and unsafe checks to what Mojo 1.2 offers. |
| F14 | The `size` check counts the code lines of the port's own `.mojo` files (generated files and tests aside) against the original's (for TS/JS with its local imports) and fails above three times plus 50 lines. A C unit whose ported functions call functions from outside the repository (a facade over glibc) is not compared, and `gate` says so. | Kept from rust-anything for Mojo ports: a port much larger than its original is usually reimplementing a library or handling cases one by one. A facade's one-line wrappers say nothing about how large a port of `strtol` should be ([glibc](docs/measurements/2026-11-22-glibc-facade.md)). |
| F15 | Mojo has no unwinding panics: the dispatcher's `{"panic"}` answer covers dispatcher failures only (unknown name, wrong argument count, a value the port's type cannot hold), and a port that aborts is recorded as a crash. | An abort ends the process; there is nothing to catch, so the bridge can only check what it can before calling the port. |
| F16 | PHP and C# keep what they have (`analyze` and whole apps) in both phases. | Neither generated Rust, so there was nothing to retarget. |
| F17 | Translations of the README, the docs and the website are removed until the English text settles; the website is English only and its deploy job stays off until the user names a target. | Stale translations would misstate what the tool does. |
| F18 | C++ joins Phase 1 before the `v0.1.0` tag, on the C path: a C++ unit is a `c-abi` unit with `language: cpp`, behind a generated `extern "C"` shim and wrapper (M15-M18), on Linux only like the rest (F6). | The C path already records, builds, replays and gates a C ABI; C++ needed only the shim, the wrapper and the `cpp api` check, not a bridge of its own, and Phase 2 records the binary at the tag. |
| F19 | Phase 2 parses source through tree-sitter's Python bindings, from conda-forge in the repository's `pixi.toml`: `tree_sitter` 0.26.1 (MIT; its recipe's `MIT and EPL-2.0` names two licence files, py-tree-sitter's MIT and the core's `lib/src/unicode/LICENSE`, which is the ICU/Unicode licence, with no EPL text in the package), and the grammars at the Cargo.lock versions — `tree-sitter-c` 0.24.2, `tree-sitter-cpp` 0.23.4, `tree-sitter-go` 0.25.0, `tree-sitter-ruby` 0.23.1, `tree-sitter-java` 0.23.5, `tree-sitter-kotlin` 1.1.0 (tree-sitter-grammars, the grammar of the `tree-sitter-kotlin-ng` crate), `tree-sitter-php` 0.25.1, `tree-sitter-c-sharp` 0.23.5, `tree-sitter-python` 0.25.0 — plus `tree-sitter-typescript` 0.23.2, all MIT. | Approved by the user (2026-11-23). Same grammar versions give the trees the Rust language modules read; the bindings stop at 0.26 (the Rust core is 0.27.2), so a runtime difference shows only in error recovery, which the ports decline on. TypeScript is parsed by oxc in Phase 1, so its grammar is a second parser there, not the same one. |
| F20 | Phase 2 reads TypeScript and JavaScript through oxc's own parser, the published `oxc-parser` npm package at 0.158.0, the oxc release Cargo.lock pins for `oxc_parser`: `oxc-parser` 0.158.0 (MIT, its JS loader and the wasm build it ships), its native binding `@oxc-parser/binding-linux-x64-gnu` 0.158.0 (MIT, per its package.json; a Rust N-API library that links only glibc's libc, libm, libdl, librt, libpthread and libgcc_s) and `@oxc-project/types` 0.158.0 (MIT, type declarations only). They live in `tool/oxc/` with npm's `package-lock.json` committed; `tool/build.sh` runs `npm ci` there when `node_modules` is missing. They run on the project's Node (`mise.toml`: node 24; CI's `node-version: 24`), so no Node is added to the pixi environment. | Approved by the user (2026-11-24). The Rust tool's TS facts are oxc's: its diagnostics (counted as parse errors) and its binding-aware `IdentifierReference`. tree-sitter-typescript is a second parser that reports no error where oxc reports one (`/a/gg`, a top-level `return` in `.js`), so only oxc itself can give the same plans. The npm package is oxc's own build of the same crates, so at the same release its diagnostics and tree are the Rust tool's; nothing is built from Rust source. |

## Product

| # | Decision | Reason |
| --- | --- | --- |
| D1 | A toolkit your agent drives, not a translator that calls a model itself. | No model cost or vendor lock-in; works with any agent. The checks are the part an agent cannot do reliably. Same shape as REA. |
| D2 | **Superseded** (mojo-anything ported Python first, M1, then C, Go and Ruby, TS/JS, Java and Kotlin): TypeScript/JavaScript first. | No existing tool covers TS/JS to Rust. C/C++ and Python are crowded (DARPA TRACTOR, C2Rust, Depyler). |
| D3 | Core plus one plugin per source language: `src/ts/`, then `src/lang/{python,c,go,ruby,java}.rs` on tree-sitter. | The plan, ordering, scoring and report are the same for every language; parsers, bridges and risks are not. |
| D4 | **Superseded at the end of Phase 2** (F1): written in Rust, parsing with oxc. It holds for Phase 1, whose tool is still Rust. | Fast (x18n, 27k lines, in about 0.1 s), and the tool uses the language it moves people to. |
| D5 | Shadow mode for every language. | Cloudflare FL2 ran old and new side by side in one process and moved traffic gradually. Tests prove a port; production traffic confirms it. |
| D6 | Name `mojo-anything` (was `carcinize`). Java packages use `mojoanything`, identifiers `mojo_anything`/`MojoAnything`, environment variables `MOJO_ANYTHING_*`. | Says what it does. (rust-anything's reason also cited the Rust trademark policy on "Rust" in crate and repository names; the name no longer contains it.) |

## `analyze`

| # | Decision | Reason |
| --- | --- | --- |
| A1 | A unit is a folder, or a file directly in a package's source root. | Folders are how most codebases mark modules; root files are usually standalone. |
| A2 | Skip `node_modules`, `dist`, `build`, `out`, `target`, `coverage`, `fixtures`, `__fixtures__`, `__snapshots__`, `playground`, `examples`, tool configs and `.d.ts`. | Not product code; fixtures hold sample projects that would distort the plan. |
| A3 | `.tsx`, `.jsx`, `.vue`, `.svelte`, `.astro`, and code importing Vue/React/Svelte/Nuxt or `vscode`, is kept in JS. | The prompt asked to flag UI-heavy parts; editor extension hosts make native modules painful. Their scripts are still parsed for imports. |
| A4 | Bridge: a Mojo port behind the Node-API shim (`Mojo (Node-API)`) when the unit or anything it imports needs Node, or its package's `src/` does; `Mojo (wasm)` otherwise, which `bridge` still ports for Node unless `--kind wasm` asks for the wasm module (M13). | Portable code must keep running in browsers; Node-only code gets the native bridge. Build scripts next to `src/` do not make a package Node-only. Until M4 Task 9 the two were napi-rs and wasm-bindgen. |
| A5 | Waves come from strongly connected components of the unit graph. | Leaves first means a Rust unit never calls back into JS; cycles must move together. |
| A6 | Risks are heuristics: method names like `slice` also match arrays. | False positives cost a look; false negatives cost silent bugs. Each risk lists its first lines so a human or agent can check quickly. |
| A7 | Readiness = 100 - weighted risks (log of count) - size - fan-in - dependency penalties + test bonus. | Log keeps big files from drowning in counts; fan-in pushes widely-used units later, where a mistake costs more. |
| A8 | Priority = half readiness, half value (loops and string work per line, tests, size between 80 and 600 lines). | Readiness alone picks trivial declaration files. A first port should be safe and worth the bridge. |
| A9 | The library table (`src/replacements.toml`, every language; `src/crates.toml` until M6) is hand-curated: each library maps to a Mojo stdlib module, a pixi package or `python:<module>` through CPython interop; unknown packages are reported as `unknown`, never guessed. | The prompt: flag missing equivalents instead of hand-rolling silently. |
| A10 | JSON output carries `schema: mojo-anything/analyze@1`. | Agents read it; it is a wire contract and gets versioned. |

## The loop

| # | Decision | Reason |
| --- | --- | --- |
| L1 | **Superseded** (by M2 and M6: `port.mojo` holds the port, generated files the bindings, and `gate` fails a C unit's `port.mojo` that names a pointer): `bridge` splits `lib.rs` (bindings) from `port.rs` (plain Rust, `#![forbid(unsafe_code)]`). | Binding macros expand to unsafe code; the port itself never needs it, and it stays testable without a JS runtime. |
| L2 | `bridge` refuses to write into a non-empty folder, and refuses `blocked`/`keep` units without `--force`. | A port in progress is the user's work; the plan's verdicts should not be bypassed by accident. |
| L3 | **Superseded** (by M12 and F15): napi bindings catch panics and throw JS errors (Rust era; the Mojo dispatcher answers a panic as `{"panic": ...}` and `index.cjs` throws it, see M12). | A panic unwinding into Node aborts the process; in shadow mode that would take the app down. |
| L4 | **Superseded** (Mojo ports take `String`, `Float64`, `Bool`, `List` and `Optional`, and `JsonValue` for anything structured): TS types map to `String`, `f64`, `bool`, `Vec`, `Option`; anything structured crosses as JSON. | Faithful to JS (numbers are f64) and always compiles; the port can introduce real types behind the binding. |
| L5 | `record` generates deterministic inputs from parameter types, with edge-case corpora, and derives one string argument from another half the time. | Reproducible recordings; search-like functions rarely hit on unrelated random strings. |
| L6 | Recording and diffing run in Node through generated scripts, with a lossless codec (`undefined`, `NaN`, `-0`, BigInt, Map/Set, key order, lone surrogates). | The comparison sees exactly what a JS caller sees. Lone surrogates were found by the fixture tests: JS `slice` can split emoji. |
| L7 | Both sides throwing counts as agreement; messages are not compared. | Error text is rarely a contract and would make every port fail on wording. |
| L8 | **Superseded** (by M13): wasm builds used `cargo` + `wasm-bindgen-cli` (version-checked), not wasm-pack (Rust era; removed with wasm-bindgen, see M12). | wasm-pack downloads tools at run time, which fails offline and in locked-down CI. |
| L9 | Shadow mode returns the original's result, runs the port second, and never lets the port's errors reach callers (in rust-anything the port was Rust; it is now Mojo). | Shipping shadow code must not change behavior; only the report sees the port. |
| L10 | The MCP server is a small hand-written JSON-RPC loop on serde_json. | The stdio transport needs four methods; an SDK would add churn for no gain. |

## Learned from porting x18n's core

| # | Decision | Reason |
| --- | --- | --- |
| X1 | `bridge` keeps exports in TS when their types hold functions (followed through imports, re-exports and `extends`), when they are generic, iterators, RegExp, or use `instanceof`; `--keep` adds more by hand. | 26 of x18n core's 55 exports are of this kind; ported, they would have changed the public API or broken silently. |
| X2 | Structured values cross with markers for `undefined`, NaN/Infinity/-0 and lone surrogates; the loader pads omitted structured arguments with `undefined`. | Each one produced real mismatches: `splitKey`'s `namespace: undefined`, `toWireRange` with NaN, `diffText` splitting an emoji, `isOutdated(change)` with one argument. |
| X3 | Overload signatures (no body) are skipped; type predicates map to `bool`; aliases resolve through imports; untyped defaults take the default's type. | `definePlugin` was listed twice; `isMessageLeaf` returned JSON; `KeyString` became JSON instead of `String`. |
| X4 | `record` installs a resolve hook, takes `--resolve-from`, and retries with `--experimental-transform-types`. | x18n's sources import without extensions, need `valibot` and `nostics`, and use parameter properties. |
| X5 | `bench` is a separate step, not part of `gate`. | Speed is not correctness, but it decides whether a port should ship: every x18n core port was correct and slower. |
| X6 | Risk guidance names `shift_remove` and UTF-16 string ordering. | `serde_json::Map::remove` reorders keys under `preserve_order`; JS `<` on strings compares UTF-16 units. |

## More languages

| # | Decision | Reason |
| --- | --- | --- |
| M1 | Every language maps its types into the TS-like dialect (`string`, `number`, `int`, `T[]`, `Record<string, T>`, `T \| undefined`). | The planner, input generator and port stubs stay one implementation; a language plugin only discovers, scans, resolves and lists exports. |
| M2 | Python uses a Mojo Python extension module (`PythonModuleBuilder`, built with `mojo build --emit shared-lib`), C a plain C ABI, Go and Ruby one Mojo JSON dispatcher (`dispatcher.mojo`, exporting `mojo_anything_call` and `mojo_anything_free`, JSON through EmberJson), and Java and Kotlin the same dispatcher through the Foreign Function & Memory API (M14), each behind a generated wrapper with the original API. Go also gets typed cgo exports (`exports.mojo`) for functions whose parameters and results are all numbers, booleans and strings; a unit made only of those needs no JSON. | The extension module and the C ABI are each language's native extension path; PyO3 was dropped with the move to Mojo, and an old PyO3 manifest asks for a fresh `bridge`. One dispatcher keeps the port's side identical across languages, and the generated wrapper keeps callers unchanged. |
| M3 | `diff` goes through the same wrapper callers will use (cgo package, Fiddle file, Java wrapper classes, the Python package around the Mojo extension). | The test must see what callers see: wrapper bugs, type conversions and exception mapping included. |
| M4 | Record and diff run in the source language's own runtime, with generated drivers; nothing is written into the original repository (Go builds its driver as a separate module with `replace`). | The original must run exactly as it does for its callers, and mojo-anything must not edit code it is migrating. |
| M5 | C records each case in a forked child; a crash is recorded as `crash: <signal>` and accepts any port behavior. | Inputs outside a C function's contract are undefined behavior: real glibc segfaults on `isalpha(INT_MAX)`. |
| M6 | C units port to Mojo drop-in shared libraries that export the original names with the original signatures. `port.mojo` sees no pointers: a `const char *` arrives as `Optional[Span[UInt8, ImmutAnyOrigin]]` (`None` for `NULL`), byte inputs and buffers as `Span`s, an `int *` as `mut Optional[Int32]`, a `char **` into an input as an offset, structs of scalars by value. `exports.mojo` alone reads and writes pointers, each with a `# SAFETY:` comment, and `gate` fails a `port.mojo` that names a pointer type. Pointers to lists, variadics and ownership-carrying returns stay in C. An old Rust `c-abi` crate (a folder with `Cargo.toml`) asks for a fresh `bridge`. | Ownership of buffers and structs has to be designed, not guessed; with the pointers kept in one generated file, the port is plain Mojo that cannot write past a buffer. |
| M7 | Errors compare by exception type (Python, Ruby), Java exceptions by class and message (since M5), Go `error` values by message, Go panics by being panics. A port signals one with `Err("TypeName: message")` (Mojo: `raise Error("TypeName: message")`). | Messages are rarely a contract, except Go's error strings, which callers often compare, and the JDK's, which M5's plan makes part of the port (`For input string: "x"`); every Java and Kotlin port here already gave the original's messages when the check was added. |
| M8 | Unannotated parameters used as numbers become `number` (Python, Ruby); Python recording passes integral numbers as ints in every fourth case. | `colorsys` got 1,709 garbage cases out of 1,800 without inference, and its int results were never recorded without ints. |
| M9 | **Partly superseded** (no crate is generated any more; Mojo units read floats through EmberJson, F4): `serde_json` runs with `float_roundtrip` in mojo-anything and in every generated crate. | The default parser can be one ULP off; Java's `Double.toString` exposed it in 43 cases. |
| M11 | Go and Ruby lost their Rust bridges: magnus (Ruby's extension), Go's binary wire and the Rust dispatcher. Ruby reaches the Mojo dispatcher through Fiddle, from a generated `ruby/<lib>_native.rb`. Integers beyond 64 bits and lone surrogates are refused with a named error. A Rust-era Go or Ruby unit (a folder with `Cargo.toml`) asks for a fresh `bridge`, and `--batch` for either answers "not yet". | Only Rust is banned, and Fiddle ships with Ruby; magnus and the wire were Rust. EmberJson reads integers up to 64 bits, so a bignum would otherwise arrive as a wrong float. Batches return once a Mojo batch path exists. |
| M12 | TS/JS units reach Mojo through a Node-API C shim (`node_shim.c`, compiled with `cc` against Node's headers) over the same JSON dispatcher as Go and Ruby, loaded by a generated `index.cjs` that keeps the original API, error classes and markers. napi-rs and wasm-bindgen are gone, with the binary wire of S7, the napi/wasm batch classes and `bridge --allocator`; an old `napi` or `wasm` manifest asks for a fresh `bridge`. `bridge` defaults TS/JS units to `mojo-node` (`--kind wasm` gives M13's `mojo-wasm`), and `package` answers "not yet" for npm until the packaging plan (M7). A recorded error never agrees with a port's `not ported: ` stub or `panic in <name>:` answer. | Only Rust is ruled out, and napi-rs and wasm-bindgen are Rust: the port must be Mojo, and Node-API is Node's own C ABI, so a few dozen lines of C are all that sit between them. The binary wire is deferred: JSON through the dispatcher is the one path until `bench` shows where a faster crossing pays on Mojo. |
| M13 | `bridge --kind wasm` (`mojo-wasm`) compiles the same JSON dispatcher to a wasm64 (memory64) module that the generated `index.cjs` instantiates in place of the Node-API addon. The unit's own Mojo 1.2.0 writes the IR for a baseline x86-64 CPU (`--target-cpu x86-64`, no SSE intrinsics), the IR is retargeted to `wasm64-unknown-unknown` (and its new float-constant syntax rewritten), and mojo-wasm's clang 22 and wasm-ld (`MOJOWASM_HOME`, default `~/github/mojo-wasm`) compile and link it with `src/mojo/wasm_runtime.c`: a bump heap behind Mojo's allocator, `malloc` and the host, reset after every call, a stack-trace stub so `raises Error` works, and 128-bit multiply and shifts. Floats are written by EmberJson as on native; the module must export the dispatcher and import only `env.mw_write`. A trap answers as a panic and starts a fresh instance. Needs Node 24+ (or a browser with memory64). | mojo-wasm's own wasm32 route does not carry the dispatcher: its pinned nightly cannot compile EmberJson 0.5.0, 64-bit IR read with 32-bit pointers folds the call to an endless loop, and IR for a 32-bit target (riscv32, i686, x32) breaks Mojo's `Variant` (its size and its layout disagree, so a growing `List` of JSON values loses tags). On wasm64 every probe matched native, and `String(Float64)` does not hang. |
| M14 | Java and Kotlin units reach Mojo through the Foreign Function & Memory API (`java.lang.foreign`, Java 22+, no preview features): generated `<Lib>Native` and wrapper classes with the original static methods call `mojo_anything_call` and `mojo_anything_free` of the same JSON dispatcher as Go, Ruby and TS. `bridge`, `record` and `build` stop on an older JDK. The Rust JNI crates are gone, and with them the Android profile (`build`, `record` and `diff --profile android`, the NDK and device support: `--profile` takes only `host`) and the Java binary wire and batches (S5, S6, S11, S14); a Java or Kotlin manifest of kind `ffi` asks for a fresh `bridge`, and `--batch` on `mojo-jvm` answers "not yet". | Only Rust is ruled out, and JNI needed native code on the Rust side; FFM is the JDK's own C ABI and needs none. Mojo does not target Android, so a port could not run there. The binary wire was Rust; it is deferred until `bench` shows where a faster crossing pays on Mojo (the JDK facade: about 1 µs per call, 0.03x). |
| M10 | Shadow per language: a Go package, a Ruby file that `prepend`s, `<Class>Shadow` Java classes, a C file with `-D` renames linked to the Mojo unit's shadow library (only the `mojo_anything_` names), and a `shadow` crate feature where the bridge is still Rust (superseded: no bridge is Rust any more; TS/JS shadows load the Mojo unit's `index.cjs`). | Each is the least invasive drop-in that language allows. |
| M15 | C++ units reuse the C path: a unit is `kind: c-abi`, `language: cpp`, and only generated C++ sees C++ types. `cpp/shim.cpp` gives each function one C symbol, `cpp__<namespace>__<name>` (`::` as `__`), with a string as a pointer and a byte length, a vector as a pointer and an element count, a string or vector result in memory the callee `malloc`s with its length through a `size_t *`, and a final `char **` error slot; `record` compiles the original and the shim with `c++ -std=c++17 -shared` (`CXXFLAGS` after) and records them with the C driver. The Mojo port exports the same symbols; `cpp/wrapper.cpp` defines the original functions over them, and `gate`'s `cpp api` check compiles the unit and the wrapper and compares their mangled symbols with `nm`. Manifests and cases name functions by their C++ name (`kit::text::join`); `port.mojo` names them without their namespace, so two exports with the same last name are refused. tree-sitter-cpp 0.23.4 (`cargo add`; its `tree-sitter-language` interface works with `tree-sitter = 0.27`) parses C++. | A separate C++ bridge would have needed a second driver, build and set of checks, and a C++-facing ABI Mojo does not have; the shim keeps C++ to two generated files and lets every C check apply. The `cpp__` prefix keeps a global-namespace function's symbol from clashing with its own C++ declaration (`extern "C" int add(int, int)` beside `int add(int, int)` does not compile). Mangled names are what a C++ caller links against, so they are the API to check. The wrapper replaces only the bridged functions, so `cpp api` also fails on any other strong external definition (`T`, `D`, `B`, `R`) of the unit's file, and the bridge note says to keep those in a file of their own; weak ones (`W`, `V`: inline functions, implicit members, template instances) are left out, since every file that uses them emits them again, at the cost of missing an explicit template instantiation. No "rest" file is generated: cutting a C++ file apart by hand-picked definitions is the user's call. A `std::string` argument becomes a Mojo `String` only if it is UTF-8; otherwise the export raises a `std::invalid_argument` ("`<param>` of `<function>` is not valid UTF-8"), a documented known limit (no byte crossing for strings yet). |
| M16 | Exceptions are not detected: any C++ call may throw, so every shim symbol wraps its call in `try` and writes `<type>: <what()>` (the type demangled with `abi::__cxa_demangle`, `std::domain_error: negative input`) or `unknown exception` to the error slot, which the driver records as the case's error. A type the wrapper cannot throw itself is recorded as `<type> (<base>): <what()>`, `<base>` being the nearest of the nine `<stdexcept>` types, `std::bad_alloc` or `std::exception` (a `dynamic_cast` chain; `std::system_error` lands on `std::runtime_error`). A port raises `Error("<text>")` with the recorded text; the wrapper throws the named standard type, or for `<type> (<base>)` the base, with the `what()` text (`std::exception` as a private subclass carrying it; `std::bad_alloc` with its own text), else `std::runtime_error` with the whole text. `gate` warns (`cpp exceptions`, passing) for each derived type the recording shows. | No exception may unwind through `extern "C"` or Mojo, and no static check can tell which calls throw. Comparing type and message matches M7's Java rule. A derived type is usually defined in the unit's own file or a header the wrapper does not include, so the wrapper cannot throw it; its base keeps every `catch` of a standard type and every `what()` working, and the recorded text keeps the derived name for diff. |
| M17 | `bench` for C++ units runs the driver's bench mode: both the original (through the shim) and the port are called through ctypes with the recorded arguments. | The C path's bench links the original and a shadow library into one C program, but the shim and the port export the same symbols; timing both through the same crossing keeps the comparison fair, at the cost of numbers dominated by the ctypes call for small functions. |
| M18 | C ABI units, C and C++, build with `mojo build --fp-mode contract=off`, and `record` compiles the original with `-ffp-contract=off` (`CFLAGS`/`CXXFLAGS` come after, so a project's own flags win). Neither side fuses `a * b + c` into a multiply-add, and a port is written as the original's statements, with no hand-placed rounding. | By default `mojo build` contracts a product and a sum into one multiply-add (`--fp-mode contract=fast`), while g++ 13.3 at `-O1` for x86-64 rounds them separately: the EnergyPlus psychrometrics port, written as the C++ reads, missed about one case in seven by one or more units in the last place. A hand-placed `@no_inline` multiply fixed one port; the compilers' own flags fix every port and every original alike. A recording is only as representative as its flags: g++ also fuses at `-O2 -march=native` or with `-mfma`, so a project built that way records with its own flags. |

## Speed

| # | Decision | Reason |
| --- | --- | --- |
| S1 | **Superseded** (Rust era: Python moved to the Mojo extension in M1, Java to FFM in M5, see M14; Go's typed cgo functions live on as `exports.mojo`, M2): No JSON text on the hot path: Python converts objects in Rust (`pyconv.rs`), Java and Go get typed JNI and cgo functions for numbers, booleans and strings; JSON remains the fallback for other types in Java and Go. | JSON cost 10-50x the work: the colorsys port took 11.7 µs per call, CPython 0.5 µs. |
| S2 | **Superseded** (by `PyNum` in `py_num.mojo`, which keeps the same int-or-float semantics in Mojo ports): Ports of untyped Python can use `pynum::Num`, Python's int-or-float, instead of `serde_json::Value`. | A `Value` per number cost about 600 ns per call in colorsys; `Num` keeps ints as ints at native speed. |
| S3 | `bench` decodes arguments once and times only the calls, in the original's process; C benchmarks link the original (renamed with `-D`) and the port into one C program. | Decoding per call, or calling through ctypes, hid the difference being measured. |
| S5 | **Superseded** (Rust era, removed in M5, see M14): Java (Go until the Mojo move, see M11): types beyond numbers, booleans and strings (lists, arrays, maps, structs, boxed and optional values, several results) cross as a compact binary wire, with encoders and decoders generated per type on both sides; the JSON dispatcher is only the fallback for types the wire cannot express. | `encoding/json` and the Java JSON codec cost 5-8 µs per call; the wire costs 0.4-1 µs, and a Java `List<String>` function became faster than Java. |
| S6 | **Superseded** (Rust era, removed in M5, see M14): Java ports report errors through a per-thread `String[2]` slot passed with each call; the generated Java throws the exception (constructors cached as method handles). Native code throws only for null arguments. | An exception raised from JNI costs about 1.5 µs more than one thrown in Java: the JVM unwinds the calling compiled frame on a slow path. A throwing `parseRadix` went from 3.0 to 1.8 µs; calls that succeed cost the same. |
| S7 | **Superseded** (Rust era, removed in M4 Task 9, see M12): TS (napi-rs and wasm-bindgen): synchronous functions with structured arguments or results get generated JS encoders and decoders over two buffers registered once (napi) or wasm memory (wasm). Objects travel by field index in the caller's key order, strings as UTF-16, unmodeled types as tagged values. Arguments of another shape, and port results that do not fit the TS type, send that call through JSON. | napi's own object conversion is 2-3x slower than JSON (one napi call per property); a hand-written wire prototype was 6-7x faster. Across the nine x18n core units the bridge cost fell by a third on average and `buildTree` became 2x faster than TS; the other leaf functions stay slower than V8's JIT. |
| S8 | `profile` runs a real workload under the language's own profiler (`node --cpu-prof`, `cProfile`) and ranks the repository's functions by inclusive time, with callers and the argument that varies per call. | Which code to port is a property of how it is called, not of the code: x18n's `fuzzyScore` is a leaf (slower in Rust per call) but a quarter of a search, called 50,000 times by one loop. |
| S9 | **Superseded in part** (Mojo batches: S17, one thread, `rank` in JS): Batch classes (`--batch fn:param`): the items cross once, then `run` maps the function over all of them and `rank` returns the indexes of results above a minimum, best first (stable, like JS `sort`). Items and results are scalars or strings; numbers come back as typed arrays. | Research and a prototype agreed: the gains come from keeping data on the Rust side and using all cores, not from faster crossings. Indexes, not strings, cross back: the caller already holds the items. |
| S10 | **Superseded** (Rust era; Mojo ports have no custom index yet, S17): A `<Function>Index` struct in `port.rs` (`new(items)`, `run(fixed args)`) replaces the default per-item loop; every crate with batches depends on rayon, wasm included, where it runs on one thread. | Preparing items once (lowercasing, masks) was the second 4x on x18n search; one `port.rs` then builds for napi and wasm. |
| S11 | **Superseded** (Rust era; Go and Ruby moved in M3, see M11, Java and Kotlin removed in M5, see M14): Batches in every bridged language (Go and Ruby until the Mojo move, see M11): magnus classes in the original Ruby module (the original's defaults and keywords kept), a Go type over a Rust handle (`New…`, `Run`, `Rank`, `Close`, a finalizer), and a Java `AutoCloseable` class freed by `close` or a `Cleaner`. Go strings cross packed in one buffer. | The same pattern pays everywhere: Go and Java, where per-call ports lose, gain 3-4x. |
| S12 | **Superseded** (no Rust crate is generated any more): Rust crates with batches (Java and Kotlin JNI crates, removed in M5) use mimalloc as Rust's global allocator. `bridge --allocator rusty_alloc` (napi and wasm crates) went with those bridges in M4 Task 9; a manifest's old `allocator` field is ignored. | Ports allocate per item, and the system allocator serialized the threads: 1.6x on 4 cores in pure Rust, slower than one thread inside a Go process; 3.2x with mimalloc. Only Rust code uses that heap: every buffer that crosses is copied or freed by Rust. rusty_alloc is an option, not the default: the allocator lands in every generated crate, and mimalloc has years of production use behind it. Measurements by its maintainer are in #96 and #112. |
| S13 | `profile` per runtime: node `--cpu-prof`, cProfile, `go test -cpuprofile` read through `go tool pprof -raw` (inlined frames kept), JFR execution samples (`jfr print --stack-depth 256`), and for Ruby a TracePoint call tracer loaded through `RUBYOPT`. Sampled stacks share one aggregator; the batch parameter is found from each language's loop forms. | Each is the profiler that ships with the runtime; Ruby has none built in that samples, and stackprof is a gem the repository may not have. |
| S14 | **Superseded** (Rust era, removed with the Go, M11, and Java, M14, bridges): String results go back in bulk: Go allocates one buffer of the results' total size and Rust copies into it on all cores (Go reads it with `unsafe.String`, one slice per result); Java gets one `char[]` of UTF-16 encoded on all cores, plus the lengths, and slices it with `new String(chars, at, len)`. Typed JNI strings cross as UTF-16 (`GetStringRegion`, `NewString`), not modified UTF-8. | Joining and freeing results on one thread, a second copy in Go, and one JNI call per Java string cost as much as the work: Java's batch went from 25 to 14 ms, its per-call port from 90 to 63 ms. |
| S15 | **Superseded** (Rust era, with S10): An index in `port.rs` may define its own `rank(<fixed>, min)`; the generated `rank` of every language then calls it instead of ranking `run`'s results. | Ranking can be cheaper than scoring everything: x18n's index narrows to the last query's matches and reads one-letter queries from a table, 0.8 to 0.5 ms per query, 1.7x to 11.5x on wasm. |
| S16 | `setup` writes each agent's own config (`~/.claude.json`, `~/.codex/config.toml`, `~/.cursor/mcp.json`, `~/.gemini/settings.json`, `~/.config/opencode/opencode.json`) and skills folder, adding only the `mojo-anything` entries, keeping key order, writing through a temporary file, and refusing files that do not parse. The command is the running executable's absolute path. OpenCode reads `mcp.servers` and takes the whole argv in `command`, so its entry is an array and a server left `disabled` is turned back on. | One command to try it in any agent is what most people need first; a tool that rewrites someone's settings must never lose them. |
| S17 | Mojo ports of TS/JS units batch through the dispatcher: the JS batch class checks and encodes its items once, each `run` sends them in one `<function>:batch` call that calls the port per item on one thread, and `rank` sorts `run`'s numbers in JS. No item table lives on the Mojo side, and there is no custom `Index` yet. | One crossing per run instead of one per item is where most of the win was; a table of handles in the library and `parallelize` wait until they are measured. |
| S4 | `bench` ends with a verdict: ship, keep the slower functions, port a bigger unit, or (for C) optimize the port. Faster is 1.1x or more, slower under 0.9x. | Numbers alone left the decision to the reader; Go and Java leaf functions cannot win per call, and the tool should say so. |

| # | Decision | Reason |

| W1 | The CLI front door is a Mojo binary in `mojo/app` (a pixi project: `main.mojo`, `original.mojo`, `units.mojo`), built with `mojo build --Werror` into `mojo/app/.mojo-anything/build`, with the repository passed as `-D MOJO_ANYTHING_REPO=<repo>` (read with `get_defined_string`); at run time `$MOJO_ANYTHING_REPO` wins, and without either the binary finds the repository five folders above itself. | Its own build folder keeps two front doors from overwriting each other's binary; the define and the variable find the original through a symlinked `mojo/` (pitfalls). |

## Known limits

- Tests that import a package by name credit the package, not a unit.
- `analyze` still guesses "compute-heavy" from loops and string work; `profile` measures (not for C:
  use `perf`). Go workloads must be `go test` runs, since Go profiles only from inside the process.
  The Ruby tracer slows the program several times; shares stay comparable.
- The bridge copies strings and structured values on every call. For fine-grained functions this
  dominates: measure with `bench`, and batch the loop around them. Batches take one scalar or
  string parameter (Ruby: any value) and return scalars or strings; not for C.
- Shadow mode compares synchronous port results; functions that mutate their arguments are run on
  already-mutated input by the second implementation.
- C: scalars, `const char *`, byte buffers, `int *`, a `char **` into an input and structs of
  scalars by value cross the bridge (M6); pointers to lists, variadics, state structs and returns
  that carry ownership stay in C. Functions defined through macros are not seen.
- C++: free functions over integers, floating-point numbers, `bool`, `std::string` and
  `std::vector` of numbers (by value or `const&`), defined in a `.cpp`/`.cc`/`.cxx` file. Classes,
  member functions, templates, overloads, state objects, pointers, references the function writes
  through, `inline` and `constexpr` definitions stay in C++ with the reason: bridge a free-function
  facade over them. No `shadow`, `--batch` or front door for C++ units yet.
- Go: methods, generics, variadics, pointers, interfaces and channels stay in Go; struct
  parameters cross as JSON with their exported fields.
- Ruby: module functions only (`def self.x`, `module_function`); classes and methods that take
  blocks stay in Ruby. Without YARD tags, parameters not used as numbers cross as untyped JSON.
- Java: `public static` methods of public classes only; overloads, generics, `char` and object
  types stay in Java. `record` compiles the module's sources with `javac` alone, so code that
  needs Maven dependencies on the classpath cannot be recorded yet.
- No way yet to mark a recorded case as undefined behavior that does not crash (`ispunct(1000)`);
  remove it from `cases.jsonl` by hand.
- Go and Java: leaf functions were faster in their own language on rust-anything, since one call
  into Rust cost more than their work, and `bench` recommends porting bigger units there; this has
  not been measured on Mojo yet (F11). Interfaces, pointers,
  channels, Java objects other than strings, lists, arrays and maps, and Java primitive arrays
  other than `int[]`, `long[]`, `double[]` and `boolean[]` still cross as JSON.
- Ruby: aliases made with `alias` copy the original method, so shadow mode does not see calls
  through them.
