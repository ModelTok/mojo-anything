# mojo-anything: design

Date: 2026-11-21. Status: awaiting approval.

## Intent

mojo-anything is rust-anything redone for Mojo, in two senses:

1. **It ports code into Mojo.** Point it at a TS/JS, Python, C, Go, Ruby or Java project and it
   records what the original does, an agent writes the Mojo replacement one unit at a time, and
   every unit is checked against the recording before the next one starts. The method is
   rust-anything's ("it doesn't translate code; it proves the rewrite"); only the target changes.
2. **It is written in Mojo.** The tool itself (today 52,163 lines of Rust in `src/` plus 8,268 in
   `tests/`) is ported to Mojo with its own method: record the Rust binary, put a Mojo
   front door in front of it, move subcommands over until nothing falls back, then delete the Rust.

Why the user wants this has not been stated. The design does not depend on it, but it would
change priorities (speed claims, Python-first audience, a showcase for Mojo); ask before
publishing anything.

## Order (decided)

The user chose, in this order:

- **Phase 1, retarget.** Change the existing Rust tool so everything it generates, builds and
  gates is Mojo instead of Rust. The tool stays in Rust and keeps its tests.
- **Phase 2, self-port.** Port the retargeted tool to Mojo command by command, proven against
  recordings of the Phase 1 binary.

Retargeting first means the Rust-only generators (napi, PyO3, magnus, cargo builds, clippy gate,
about 10k lines) are replaced once in Rust and never ported to Mojo, and the Phase 1 binary's
recordings become Phase 2's specification.

## Approaches considered

| | Approach | Trade-off | Outcome |
| --- | --- | --- | --- |
| A | Fresh Mojo core, Python source only, grow later | Fast first result; most features lost for a long time | Not chosen |
| B | Port the whole tool with its own method | Keeps every feature that Mojo can support; months of work | **Chosen** |
| C | Mojo CLI on top of the Rust engine | Fastest to every feature; most of it stays Rust | Rejected: contradicts "written in Mojo" |

Within B: retarget first (chosen) versus port first, then retarget (would port the Rust
generators only to rewrite them).

## Goals

- `mojo-anything` ports units from TS/JS, Python, C, Go, Ruby and Java/Kotlin into Mojo, with
  `analyze → bridge → record → port → build → diff → gate` working for each, and is re-verified on
  the same real code rust-anything used (CPython `colorsys.py`, Go `path`, Ruby `shellwords.rb`,
  ffmpeg libavutil, vercel/ms, Fuse.js, ...). Every claim in `docs/STATUS.md` is re-measured for
  Mojo or removed.
- Whole apps: `app record`, `app replay`, a Mojo front door with fallback to the original, `wire`
  and `lift`, for CLIs first.
- The MCP server, the agent skill and `setup` keep working under the new name.
- At the end of Phase 2, the repository has no Rust: the tool is Mojo, built with pixi, and passes
  the recorded cases of the Phase 1 binary with 0% fallback.

## Non-goals

- Android (`build --profile android`, on-device recording): Mojo does not target Android. Removed.
- Native Windows: Mojo builds only on Linux and macOS. The tool runs in WSL on Windows; CI runs on
  Linux and macOS.
- Rust as a target. Nothing generated by mojo-anything is Rust.
- Keeping the 18 translated READMEs in step during the rewrite. They are removed in Phase 1 and
  can come back once the English text settles (my call: stale translations would misstate what
  the tool does).
- Upstream contributions. This is a separate product, not a PR to erkamyaman/rust-anything.

## Anti-goals

- A claim not measured on Mojo. Every number and "Verified" row in the docs is from a Mojo run;
  rust-anything's numbers do not carry over.
- A port step that "passes" because it ran the original (see pitfalls: replay without `--build`).
- Translating Rust to Mojo line by line by script and calling it done without replaying the
  recordings.

## Constraints

- **Toolchain.** Mojo via pixi (`pixi run mojo ...`), pinned in a committed `pixi.toml` and
  `pixi.lock`. Pretrained Mojo knowledge is stale: check every API against the pinned stdlib
  source and changelog before using it (Modular's `mojo-syntax` skill, mojolang.org/docs).
- **Where work happens.** A clone in WSL Ubuntu 24.04 at `~/github/mojo-anything`, not
  `/mnt/c` (the Windows checkout is CRLF). No Mojo toolchain is installed there yet.
- **Phase 1 is still a Rust change**: `cargo fmt`, `cargo clippy --all-targets -- -D warnings`,
  `cargo test`, and `docs/STATUS.md` updated, per `CLAUDE.md`. Pitfalls in `docs/pitfalls.md`
  still apply wherever the mechanism survives.
- **Repository.** `origin` points at `Tokarzewski/rust-anything` (a fork). mojo-anything needs its
  own remote before anything is pushed; the user decides the name and visibility.

## Phase 1: retarget to Mojo

### What changes and what stays

Stays as it is (target-independent): source analysis (`ts/`, `lang/`, tree-sitter), recording
and replay of cases (`harness*.rs`, `recording.rs`, `tolerance.rs`, `js_number.rs`), `app record`
and `app replay`, `fuzz`, `profile`, `bench`, `map`, the MCP server's protocol, `doctor`.

Replaced: the generated port project, the bridges, `build`, `gate`, `package`, the front door and
`lift`, `crates.rs` (library mapping), and every user-facing "Rust" string.

### The generated port

`bridge` writes a pixi project under `mojo/<unit>/` (in place of `rust/<unit>/`):

- `port.mojo`: stubs with the original names and Mojo types derived from the source signatures;
  helpers stay private (pitfall: a public helper joined the bridged API).
- the bridge layer for the source language (below);
- `pixi.toml` pinning the same Mojo as mojo-anything itself;
- tests (`test_*.mojo`) the gate runs.

### Bridge per source language

| Source | How the original calls the Mojo port | Notes |
| --- | --- | --- |
| Python | Mojo Python extension module (`PythonModuleBuilder`, `mojo build --emit shared-lib`); generated wrapper package keeps the original import path | First to verify (`colorsys.py`) |
| C | Drop-in `@export` functions with the original names and C signatures, `abi("C")` | Pointer and struct cases as in `tests/c_*.rs` |
| Go, Ruby | One C-ABI JSON dispatcher, `mojo_anything_call(name, args_json) -> result_json` plus `mojo_anything_free`, reached through cgo and Fiddle; answers `{"ok"}`, `{"error"}` or `{"panic"}` as `codegen_ffi.rs` does today | |
| TS/JS | The same dispatcher, reached through a small generated Node-API C shim | My call; a Mojo-to-wasm bridge is the later alternative |
| Java, Kotlin | The same dispatcher, reached through the Foreign Function & Memory API instead of JNI | Decided: Java 22+ |

The dispatcher needs JSON in Mojo. mojo-anything emits a small JSON reader and writer into each
port that needs it (only when needed: pitfall about unused helpers), with:

- exact float round trip and V8's shortest digits for JS callers (pitfall: ties), tested on ties;
- key order preserved;
- no recursion limit on input depth (pitfall: 128 levels).

Dropped from Phase 1, possibly later: the binary wires (`codegen_tswire.rs`, `wire.rs`) and the
native batch classes (`codegen_batch_native.rs`). They are speed features; correctness first.

### build, gate, package

- `build`: `pixi run mojo build` for the unit (shared library or extension module), into the
  unit's own build folder (pitfall: shared target folders).
- `gate`, the definition of done, adapted:
  - `mojo format --check` clean;
  - the build is free of warnings (warnings are errors);
  - the unit's Mojo tests pass;
  - every function ported (no stub left);
  - no unexplained `abort()` or unsafe pointer use (each needs a comment saying why, as `// SAFETY:` does today);
  - the built module exposes the original API;
  - the recording replays cleanly against the built module, not the original.
- `package`: Python wheels with the extension module for Linux and macOS first; npm, gem and Go
  packaging follow once their bridges are verified.

### Whole apps

- The front door is a Mojo binary at `mojo/app/` that owns the entry point and falls back to the
  original for anything not ported, with `original.run_with_stdin` for per-case decline (pitfall).
- `lift` refuses while any glue still falls back.
- CLIs first. Servers need sockets: Mojo has no HTTP in its stdlib, so a server front door is the
  builder's call (libc sockets through `external_call`, or Python interop), decided once a CLI
  works end to end.

### Naming

Binary, crate, MCP server name, skill, plugin, npm wrapper and website become `mojo-anything`.
Generated folders `mojo/` instead of `rust/`, work folder `.mojo-anything`, environment variables
`MOJO_ANYTHING_*`.

### Phase 1 done when

- Each source language's fixture loop (`tests/loop.rs` and friends) runs with Mojo ports, and
  CI passes on Linux and macOS (CI runs on macOS and Windows today; the Linux job is new and the
  Windows job goes).
- The real-world runs are redone in Mojo at least for `colorsys.py`, Go `path`,
  `shellwords.rb`, one ffmpeg unit and vercel/ms, with results in `docs/STATUS.md`.
- One CLI is lifted to a pure Mojo binary.

## Phase 2: port the tool to Mojo

### Method

1. **Record the Phase 1 binary.** `mojo-anything app record` on itself, every subcommand over the
   repository's fixtures (`tests/fixtures/*`, `demo/`), including the files each command writes.
   Commands that regenerate files are recorded from stale fixtures (pitfall). The MCP server is
   recorded as stdin/stdout sessions.
2. **Front door.** A Mojo binary named `mojo-anything` that runs ported subcommands itself and
   execs the Rust binary for the rest, with the same arguments, stdin and environment.
3. **Move subcommands over** in dependency order, each proven by `app replay --build <Mojo
   binary>`, reading the fallback line (pitfall).
4. **Port the tests.** Rust `#[test]`s become Mojo tests alongside the code they cover.
5. **Lift.** When every recorded case is answered in Mojo, delete the Rust and the fallback.

The Phase 1 tool can only bridge into Mojo from the six source languages, not from Rust, so
Phase 2 works at command level (whole-app front door), not unit level.

### Order (my proposal, for the plan to refine)

1. Plumbing: process running with stdin closed and time limits, canonical paths, case files,
   reports.
2. Commands with little parsing: `doctor`, `map`, `setup`.
3. `app record`, `app replay` (they are the proof machinery for everything after).
4. `analyze`, `bridge`, `record`, `build`, `diff`, `gate` per language, Python first.
5. `fuzz`, `profile`, `bench`, `shadow`, `package`, `front-door`, `wire`, `lift`.
6. The MCP server last, since it calls the others.

### Libraries the Rust uses, and their Mojo replacements

| Rust dependency | Mojo side (builder confirms against recordings) |
| --- | --- |
| tree-sitter and grammars | Python `tree_sitter` bindings through Mojo's Python interop |
| oxc (TS/JS parsing) | tree-sitter TypeScript grammar through the same route; outputs must match the recordings |
| serde_json | Own Mojo JSON (the same one the dispatcher uses), with the round trip rules above |
| clap | Hand-written argument parsing, help text byte-identical to the Rust binary |
| regex | Python `re` through interop, or hand-written matching where the pattern is fixed |
| ignore (gitignore walking) | Hand-written walker honouring `.gitignore`, checked on the walk fixtures |
| toml_edit, json5 | Python `tomllib`/hand-written writer; json5 through own JSON reader |

Python interop makes CPython a runtime dependency of the Mojo tool. That is acceptable
(pixi provides it) and is how the port stays feasible.

### Phase 2 done when

- `app replay --build` of the Mojo binary passes every recorded case with 0% fallback.
- The Mojo tests pass in CI on Linux and macOS.
- No `.rs` file and no `Cargo.toml` is left; `docs/STATUS.md` and `DECISIONS.md` say so.

## Calls made after the builder check

- **Where the work happens.** In this repository, on branches off `main`. Fixes landing in
  rust-anything upstream can be merged from the `upstream` remote during Phase 1. Phase 1 ends
  with a tag; Phase 2 records that tagged binary, so its specification does not move.
- **PHP and C#** keep what they have today (`analyze` and whole apps, which do not generate
  Rust), in both phases.
- **`--batch`** (`codegen_batch.rs`, verified) is retargeted in Phase 1. **`--kind wasm`** is
  retargeted after the Node-API route works, using Mojo-to-wasm.
- **Replay matching in Phase 2.** Help text and every message the tool writes itself must match
  byte for byte. Absolute paths, timestamps and outside tools' version strings and messages are
  masked by recorded normalisation rules, each listed in the recording with the reason.

## Decided by the user (2026-11-21)

- **What "written in Mojo" allows.** Only Rust is ruled out. CPython packages reached through
  Mojo's Python interop and generated C shims are fine in the finished tool.
- **Java and Kotlin** call the port through the Foreign Function & Memory API, so Java/Kotlin
  units require Java 22 or newer. The JDK 21 verification is redone on Java 22+.
- **Repository.** A new public `Tokarzewski/mojo-anything` becomes `origin`; `upstream` stays
  on erkamyaman/rust-anything for merging fixes during Phase 1.

## Left to the builder

- Exact Mojo APIs and flags, checked against the pinned stdlib (warnings-as-errors flag, export
  spelling, Python extension module API).
- How generated Mojo types map from each source language's types.
- The JSON implementation's internals, provided it meets the round-trip rules and their tests.
- The server front door's socket route.
